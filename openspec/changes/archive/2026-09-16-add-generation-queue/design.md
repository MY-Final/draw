## Context

生成是长耗时操作,而图片接口一次只跑一个请求。此前没有排队机制,用户在等待期间无法连续排单。本次补齐单通道 + 内存队列。

## Goals / Non-Goals

**Goals**
- 生成进行中仍可提交,系统按序执行,用户可见排队进度并可调整。
- 结果落到发起时的会话,不因中途切换上下文而错位。

**Non-Goals**
- 不做跨刷新持久化的队列(刷新即清空未开始项)。
- 不做并发执行或分区并行。

## Decisions

### D1:单通道 + 内存队列,上限 5
同一时间只允许一个在跑的请求。生成中再次提交则入队,`MAX_GENERATION_QUEUE = 5`;队满时拒绝并告知上限。队列仅存于内存,刷新后未开始项丢失。

### D2:排队项记住发起上下文
每个排队项记录发起时的 `workspaceId` / `conversationId`;执行时以该项自身携带的上下文落库,而非"当前"上下文,避免切走会话后结果落错地方。

### D3:对话流内原位呈现,支持提前/移除
当前会话的排队项显示在对话流尾部,标注序号;非队首项提供「提前」,所有项提供「移除」。

## Risks / Trade-offs

- **刷新丢队列**:内存态是明确取舍——低实现成本,且符合"刷新后 pending 自动收口"的既有约定。

## Migration Plan

无数据迁移。
